# The Rust timing tests: run by `scripts/rust_tests.sh timing`, one at a time,
# after `scripts/rust_tests.sh parallel` has run everything else.
#
# Why. These tests pass or fail on the wall clock. On a shared CI runner the
# other tests of the same binary (153 in hertzforge-backendd's library) hold
# the cores, the clock keeps moving while a test's own threads wait for one,
# and a correct build fails: a Sim stop ramp that takes about 40 s alone ran
# past its 180 s deadline on a three-core runner. One at a time, they get the
# cores they were written for. Nothing in them is loosened.
#
# What belongs here: a test whose verdict depends on the wall clock, not just
# its running time. It
#   - asserts an elapsed-time bound, or a rate against real time;
#   - sleeps a fixed real-time window, then asserts what happened inside it;
#   - samples another thread's transient state on a real-time poll;
#   - drives a Sim run, a daemon or a socket session on background threads and
#     waits for an outcome against a wall-clock deadline; or
#   - runs the engine with the hardware scheduling guard armed (a hardware
#     station class, or the engine's default compute budget and period-jitter
#     check with a per-tick cost that load can push past them).
# A test that only takes long, or whose timeout only guards against a hang,
# stays in the parallel pass.
#
# Format: package, target (lib, test:NAME or bin:NAME) and the test's name as
# `cargo test -- --list` prints it, one test per line. Each pass checks its
# count against this list, so an entry that no longer names exactly one test
# fails the run.
